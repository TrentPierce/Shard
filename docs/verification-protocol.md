# Speculative Verification Protocol

## 1. Overview

Shard treats speculative draft tokens as untrusted hints. When speculative mode is enabled, the verifier computes its own reference distributions for the same prompt context, accepts only safe draft positions, and deterministically regenerates from the first rejected position.

This protocol applies to:

- verifier-local speculative execution
- experimental WAN scout execution

It does not apply to browser-local answers, because those requests never enter verifier-side speculative validation.

## 2. Where It Applies

- `X-Shard-Inference-Mode: standard`
  - verifier-only generation
  - no draft verification path
- `X-Shard-Inference-Mode: local_speculative`
  - verifier-local speculative path
  - draft source stays inside the daemon boundary
- `X-Shard-Inference-Mode: experimental_wan`
  - benchmark scout path
  - draft source is an external browser scout
- Legacy aliases `distributed` and `speculative`
  - still map to `experimental_wan` for backward compatibility

## 3. Acceptance Algorithm

`ACCEPTANCE_THRESHOLD = 0.12` (KL divergence, natural log base).

```text
Input:
  draft_logits[position][vocab]
  verifier_logits[position][vocab]
  draft_tokens[position]

Procedure:
  accepted_prefix = []
  first_reject = None

  for position in 0..draft_length-1:
    p = softmax(draft_logits[position])
    q = softmax(verifier_logits[position])
    kl = sum_i p_i * ln(p_i / q_i)

    if kl < ACCEPTANCE_THRESHOLD:
      accepted_prefix.append(draft_tokens[position])
    else:
      first_reject = position
      break

  if first_reject is None:
    suffix = []
  else:
    suffix = verifier.generate_from(position=first_reject)

  return accepted_prefix + suffix
```

The key architectural point is that the verifier remains quality-bounding. Draft sources can help with latency, but they do not define the final output.

## 4. Threshold Derivation

The threshold was selected from an offline sweep over prompt-response pairs where we measured KL divergence against human-preferred continuation quality. We swept thresholds from `0.02` to `0.25` and chose `0.12` as the operating point where:

- rejection catches high-confidence wrong-token attacks
- acceptance remains high enough to preserve meaningful speculative value when a compatible pair exists

Statistically, `KL < 0.12` corresponds to distributions with close mass concentration around verifier-preferred continuations, which keeps semantic drift low while retaining throughput gains.

## 5. External Scout Audit

The verifier-local speculative path does not need contributor auditing, but the experimental WAN scout path does.

- Audit probability `P = 0.05`.
- A request selected as a golden ticket is fully generated by verifier-only inference with no external draft reuse.
- Scout draft tokens are scored against the independent verifier reference.
- Audit score is exact token match percentage over the audited span.
- If a scout wallet's golden-ticket score is below `Q = 60%`, the wallet is flagged.
- Flagged wallets receive no credits for 24 hours and remain in a forced re-audit path until performance recovers.

## 6. Adversarial Attack Vectors and Defenses

- Plausible-but-wrong draft attack: the draft source emits low-entropy logits centered on the wrong token. Defense: KL divergence rises sharply against verifier logits and rejection occurs at the first mismatched position.
- Acceptance-rate gaming: an external scout submits only easy prefixes to keep acceptance high. Defense: rolling acceptance windows plus golden-ticket audits tied to wallet-level penalties.
- Timing attack for audit detection: a scout attempts to infer golden tickets from response timing. Defense: constant-path verification envelope, jittered verifier scheduling, and delayed audit label emission so audit and non-audit timing distributions overlap.

## 7. Current Product Interpretation

- Speculative verification is still important, but it is no longer the center of the product architecture.
- The main product path is local-first browser routing plus desktop heavy inference.
- Experimental WAN scouts remain useful for compatibility testing and research, but public performance claims should be benchmarked separately from the product default path.
